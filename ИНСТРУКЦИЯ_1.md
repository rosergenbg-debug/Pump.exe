# PUMP RESEARCH LAB — ГЛАВНАЯ ИНСТРУКЦИЯ ДЛЯ CODEX

## 1. Цель проекта

Создать отдельную Windows-программу `PUMP Research Lab` (`Pump.exe`) для проекта PUMP/PumpBot.

Программа должна:

- сама скачивать необходимые публичные рыночные базы;
- обновлять уже скачанные базы только недостающими участками;
- импортировать существующие локальные данные и файл X;
- проверять полноту и качество истории;
- воспроизводить торговлю строго причинно, без знания будущего;
- запускать синтетические и исторические тесты;
- обучать ограниченную адаптивную систему выбора стратегии;
- сравнивать Champion и Challenger;
- сохранять checkpoints и продолжать обучение после перезапуска;
- формировать понятные отчёты;
- экспортировать проверенную модель в `.pumpmodel` для будущего Android-приложения.

Текущий проект не реализует реальные биржевые ордера. Только simulation, shadow и paper.

## 2. Физический результат для пользователя

Результат разработки:

- `PumpResearchLabSetup.exe` — единый Windows-установщик;
- portable ZIP как дополнительный вариант;
- ярлык `PUMP Research Lab` на рабочем столе;
- приложение работает без отдельно установленного Python;
- каталоги данных, моделей и отчётов создаются автоматически;
- пользователь управляет данными кнопками, а не вручную перемещает файлы.

Один установщик не означает один физический файл после установки. Большие базы, модели и отчёты обязаны храниться отдельно от EXE, чтобы их можно было обновлять и восстанавливать.

## 4. Автоматический Data Manager

Data Manager — обязательная центральная часть системы.

### 4.1. Режим «Скачать необходимое»

Перед тестом программа анализирует конфигурацию эксперимента и сама определяет, каких данных не хватает.

Пример:

```text
Эксперимент требует:
- PUMP trades: 60 дней;
- PUMP candles 1m: 60 дней;
- BTC candles 1m: 60 дней;
- SOL candles 1m: 60 дней;
- spread/order book: доступный период.
```

Далее программа:

1. сравнивает требования с локальным каталогом;
2. строит список отсутствующих временных диапазонов;
3. показывает объём загрузки;
4. после подтверждения пользователя скачивает только недостающее;
5. проверяет контрольные суммы и формат;
6. нормализует данные;
7. выявляет пропуски и дубликаты;
8. повторно запрашивает повреждённые части;
9. регистрирует готовый набор в DuckDB.

### 4.2. Режим «Актуализировать»

Кнопка обновления не скачивает всю историю повторно.

Она должна:

- определить последнюю надёжную временную метку;
- запросить небольшой overlap для проверки границы;
- дедуплицировать overlap;
- скачать новые записи;
- перепроверить последний незакрытый интервал;
- атомарно обновить каталог;
- сохранить журнал источника и времени загрузки.

### 4.3. Источники

Архитектура должна поддерживать сменные адаптеры:

```text
ExchangeAdapter
├── download_candles()
├── download_trades()
├── download_order_book_snapshots()
├── stream_live_trades()
├── get_rate_limits()
└── verify_continuity()
```

Первая биржа выбирается после аудита текущего PUMP и файла X. Нельзя без проверки предполагать Binance, Bybit или другую биржу.

Использовать сначала официальные публичные API и официальные архивы выбранной биржи. Для публичных данных API-ключ не должен требоваться. Если источник не предоставляет исторический стакан бесплатно, интерфейс должен честно показать это и предложить:

- работать без L2;
- импортировать купленный/внешний архив;
- начать собственный live-сбор стакана с текущего момента.

### 4.4. Форматы и хранение

- Raw-данные сохранять неизменяемыми.
- Нормализованные таблицы хранить в Parquet.
- DuckDB использовать как каталог и аналитический слой.
- JSON применять только для небольших конфигураций и метаданных.
- Не загружать всю многомесячную историю в RAM.
- Обрабатывать данные порциями.

Каждый dataset имеет manifest:

```json
{
  "datasetId": "...",
  "source": "...",
  "symbol": "...",
  "dataType": "trades|candles|orderbook",
  "startUtc": "...",
  "endUtc": "...",
  "schemaVersion": "...",
  "rowCount": 0,
  "gaps": [],
  "checksum": "...",
  "downloadedAtUtc": "..."
}
```

### 4.5. Надёжность загрузки

Обязательно:

- rate-limit handling;
- retry с backoff;
- resumable downloads;
- временные `.partial` файлы;
- атомарное переименование только после проверки;
- дедупликация;
- UTC внутри системы;
- преобразование в локальное время только в интерфейсе;
- журнал источников;

Если интервал отсутствует, он остаётся пропуском или получает явно выбранный метод восстановления. Симулятор должен знать о пропуске.

## 7. Причинный симулятор

Создать единый execution engine для всех стратегий.

Учитывать:

- комиссия 0,21% на вход;
- комиссия 0,21% на выход;
- spread;
- slippage;
- latency;
- LIMIT;
- market;
- stop-market;
- stop-limit;
- trailing stop-buy;
- TTL;
- cancel;
- partial fill;
- TP;
- SL;
- лимит входов;
- stale/disconnected data.

Все стратегии сравниваются при одинаковой модели исполнения.

Будущая информация запрещена. Если OHLC не позволяет узнать порядок TP/SL, применять консервативный результат или помечать эпизод неоднозначным.

- отскок 2,1% и продолжение падения;
- капитуляция;

- BTC shock;
- spread shock;

- stale data;
- disconnect;
- пропавшие сделки;
- одновременное попадание TP и SL.

Property tests:

Синтетика обучает механике и устойчивости, но не доказывает прибыльность.

## 10. Adaptive Strategy Router

Первая обучаемая версия выбирает только из:

- `NO_TRADE`;
- baseline X;
- LIMIT;
- higher-low entry;
- stop-market entry;
- trailing stop-buy;
- `HUMAN_ALERT`.

Сначала реализовать объяснимую модель/contextual bandit. Offline RL добавлять только после проверки Router и накопления достаточных данных.

Модель не может:

- отменить защитный стоп;
- превысить риск;
- торговать при повреждённых данных;
- использовать реальные ордера;
- бесконтрольно создавать произвольные параметры.

## 11. Награда

```text
Reward =
изменение NET-капитала
− штраф за просадку
− комиссия/spread/slippage
− штраф за хвостовой риск
− штраф за лишние перестановки заявок
```

`NO_TRADE` имеет награду 0. Его нельзя штрафовать за любое последующее движение цены, иначе система научится чрезмерно торговать.

Опасные действия блокируются action mask, а не только отрицательной наградой.

## 13. Champion/Challenger

- Champion заморожен.
- Challenger обучается отдельно.
- Challenger сначала работает только в симуляции и shadow.
- Максимальная прибыль сама по себе не даёт права на продвижение.
- Требуется независимый тест и стресс-проверка.
- Предыдущие модели не удаляются.
- Должен работать автоматический rollback.

Паспорт модели включает:

- версию;
- хеш данных;
- периоды train/validation/test;
- конфигурацию;
- random seeds;
- метрики;
- ограничения;
- статус;
- причину принятия или отклонения.

## 14. Обучение, checkpoints и производительность

Режимы интерфейса:

- `БЫСТРЫЙ`;
- `СТАНДАРТНЫЙ`;
- `НОЧНОЙ`;
- `ГЛУБОКИЙ`.

На экране показывать:

- этап;

- прошедшее и оставшееся время;
- CPU/GPU/RAM;

- Pause;

- Safe Stop.

Checkpoint обязан сохранять модель, optimizer state, конфигурацию, версии данных и прогресс.

После аварийного завершения программа предлагает продолжить последний опыт.

## 15. Экспорт в Android

Формат `.pumpmodel` содержит:

- модель;

До полной Android-интеграции создать reference loader и parity fixtures. Android не принимает модель при несовпадении схемы или контрольной суммы.

## 19. Правила работы Codex

- Один этап — отдельный commit.
- После этапа обновлять `CURRENT_STATE.md`.
- Не удалять функционал ради упрощения.
- Не скрывать отрицательные результаты.
- Не объявлять прибыльность по train-участку.

- Любое существенное изменение архитектуры сначала объяснить пользователю.

## 21. Главный принцип

Сначала необходимо доказать правильность данных, исполнения и причинного replay. Только после этого обучать модель. Красивый EXE с неверным симулятором является неготовым продуктом.
